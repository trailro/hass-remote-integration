Versions & releases

Installed = in the version store. Only one version can be deployed and running at a time; starting another version takes a backup first (pre-update-…) and keeps the config entries. Downgrading after the newer version migrated the config needs "Full rollback" (previous version + that backup).

What changed between versions

When the running integration switches versions, its entities and services just before the switch are compared with what the new version provides once it runs (after the smoke test). Removed, renamed or changed entities and removed services or fields are what break automations on the consuming side; they also raise a notification.

Patches

Bundled patches (shipped in the image under patches/<domain>/) plus your uploads in integration_manager/patches/<domain>/, applied in name order after the requirements when the integration starts (and at every boot). .py = patch module with apply(ctx)/status(ctx); .patch = unified diff (context-checked, idempotent). Headers: # integration-version: 1.2.0, 1.2.1 limits a patch to those versions (default: all), # applies-to: some-lib<2.0 retires it once the requirement moves on. Status is shown for the running version; failures never block the integration.

Check changes nothing: a diff shows where each hunk lands (or the closest lines when its context is gone), a module runs its status(ctx). Save stores the file; it is applied when the integration starts, or now with Re-apply.

YAML config

For integrations configured (fully or partly) through configuration.yaml: write here what would sit under <domain>:. Stored in integration_manager/yaml/<domain>.yaml, included in backups, validated on save (!secret resolves against secrets.yaml). Applied at boot to the running integration only, so a change needs a restart. An integration that later grows a config flow imports this YAML into a config entry the standard way.
